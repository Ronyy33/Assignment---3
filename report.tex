\section{Executive Project Summary}
% ============================================================

This report documents the architectural design, algorithmic implementation, and validation of the Jack Compiler frontend alongside a 2D Spatial Convolution application written natively in the Jack language. 

The end-to-end pipeline facilitates the lowering of high-level object-oriented Jack code down to native Hack execution binaries:
\begin{align*}
\text{Jack Code (\texttt{.jack})} &\xrightarrow{\text{Lexical Analysis}} \text{Tokens XML (\texttt{T.xml})} \\
&\xrightarrow{\text{Syntax Analysis}} \text{Parse Tree XML (\texttt{.xml}) \& VM Bytecode (\texttt{.vm})} \\
&\xrightarrow{\text{Virtual Machine Translation}} \text{Hack Assembly (\texttt{.asm})} \\
&\xrightarrow{\text{Assembler Instruction Lowering}} \text{Hack CPU Binaries (\texttt{.hack})}
\end{align*}

The deliverables are structured in two core components:
\begin{enumerate}
    \item \textbf{High-Level Application Layer}: A spatial 2D convolution engine implementing matrix processing and edge sharpening algorithms within \texttt{Conv.jack} and driver execution via \texttt{Main.jack}.
    \item \textbf{Compiler Infrastructure Layer}: A modular python-based parser suite consisting of a lexical tokenizer (\texttt{JackLexicalLexer}), code generator (\texttt{SyntaxAnalyzer}), scoped state manager (\texttt{LexicalScopeTable}), and stack-command emitter (\texttt{BytecodeWriter}), integrated with the virtual machine translator (\texttt{InstructionReader} and \texttt{AssemblyEmitter}).
\end{enumerate}

% ============================================================
\section{Architectural Breakdown}
% ============================================================

The refactored compiler frontend follows a highly decoupled, modular object-oriented design using clear boundaries of single responsibility:

\begin{description}
    \item[\texttt{JackTokenizer.py} (\texttt{JackLexicalLexer})]
    Ingests raw source text, strips nested and inline comment blocks through a deterministic character character lookup state manager, and emits categorized tokens (keywords, symbols, constants, and identifiers) into an structured XML format (\texttt{<Class>T.xml}).
    
    \item[\texttt{CompilationEngine.py} (\texttt{SyntaxAnalyzer})]
    A recursive-descent parser mapping token patterns to the formal grammar rules of the Jack language. In a highly optimized single-pass approach, it simultaneously verifies syntactical validity, writes the resulting structural parse tree XML (\texttt{<Class>.xml}), and translates active expressions into stack bytecode statements.
    
    \item[\texttt{SymbolTable.py} (\texttt{LexicalScopeTable})]
    Handles identifier mappings during compilation across class and subroutine scopes. Resolves variable attributes into a tuple containing type, scope kind (static, field, argument, local), and index offsets.
    
    \item[\texttt{VMWriter.py} (\texttt{BytecodeWriter})]
    An abstraction wrapper that structures formatting details for emitting stack-based VM instructions (\texttt{push}, \texttt{pop}, \texttt{call}, \texttt{function}, \texttt{return}) to output files.
    
    \item[\texttt{JackCompiler.py}]
    Orchestration driver that processes the source files sequentially, executing tokenization and parser compilation workflows.
\end{description}

The single-pass compilation architecture (parsing and code generation happening in tandem) minimizes allocation costs, bypassing the need to generate and traverse a large, intermediate Abstract Syntax Tree (AST) in memory.

\section{Lexical Tokenizer Design}
% ============================================================

\subsection{State-Machine Driven Comment Stripping}

A common issue in tokenizer design is comment stripping. Utilizing standard single-line regular expressions (such as applying \texttt{/\textbackslash*.*?\textbackslash*/} line-by-line) fails on multi-line block comments because the dot operator does not consume newlines.

Consider a multi-line block comment:
\begin{lstlisting}[style=pseudocode]
/* Starting a multi-line comment
   extending to this line */
let matrixSize = 5;
\end{lstlisting}

If processed line-by-line:
\begin{itemize}
    \item Line 1 contains the open token \texttt{/*} without a closing token. A single-line regex fails to match and leaves the open block untouched.
    \item Line 2 contains only the close token \texttt{*/} with no opening block, leading to similar regex match failure and syntax compilation errors.
\end{itemize}

Even applying regex globally across the entire file can be fragile; a greedy match would consume valid, operational code placed between distinct block comments. To resolve this, our tokenizer implements a deterministic character character scan state-machine. By maintaining boolean flags (such as whether the cursor resides inside a string literal, line comment, or block comment), it guarantees robust, context-sensitive comment stripping without backtracking overheads.

\subsection{Token Classification and XML Escaping}

Once stripped, the code is parsed into lexical categories based on character types: symbols, numeric digits, strings bounded by double quotes, keywords, or identifiers. Special XML entities (\texttt{<}, \texttt{>}, \texttt{\&}, \texttt{"}) are escaped safely into their matching XML representations (\texttt{\&lt;}, \texttt{\&gt;}, \texttt{\&amp;}, \texttt{\&quot;}). The replacement of the ampersand symbol (\texttt{\&}) is always executed first to prevent secondary double-escaping bugs (which would translate \texttt{\&lt;} into \texttt{\&amp;lt;}).

\section{Recursive-Descent Parser Design}
% ============================================================

The parser (\texttt{SyntaxAnalyzer}) validates the token stream against the formal Jack grammar using a recursive-descent strategy. Each non-terminal is parsed by its own dedicated method (e.g., \texttt{parse_class}, \texttt{parse_subroutine_declaration}, etc.).

\subsection{Lookahead Navigation}

The parser walks the token stream sequentially. The following primitives handle structural tracking:
\begin{itemize}
    \item \texttt{\_require\_token(type, value)}: Asserts that the active token matches the expected constraints, appends its terminal node to the XML structure, and advances the token cursor.
    \item \texttt{\_matches\_token(type, value)}: Peeks at the active token to determine layout branch choices without advancing the cursor.
    \item \texttt{\_lookahead\_next\_token()}: Looks ahead exactly one step past the active token, returning its properties.
\end{itemize}

\subsection{The LL(2) Challenge in \texttt{parse\_term}}

While the Jack grammar is mostly LL(1), parsing expressions involving terms that begin with an identifier presents an LL(2) challenge. Upon encountering an identifier, the parser cannot distinguish between a simple variable (e.g., \texttt{x}), an array lookup (e.g., \texttt{arr[i]}), or a subroutine call (e.g., \texttt{foo()} or \texttt{obj.bar()}) using only one token of lookahead.

To resolve this, the parser peeks at the next token:
\begin{itemize}
    \item If the next token is \texttt{[}, it parses it as an array indexing term.
    \item If the next token is \texttt{(} or \texttt{.}, it parses it as a subroutine call.
    \item Otherwise, it treats it as a standard variable identifier.
\end{itemize}

\subsection{Expression Evaluation and Precedence}

Jack implements strict left-to-right evaluation with no operator precedence. Expression parsing is structured inside the \texttt{parse_expression} method:

\begin{lstlisting}[style=pseudocode, caption={Syntactic Parsing of Expressions}]
parse_expression:
    parse_term()
    while current_token in math_operators:
        operator = require_token(symbol)
        parse_term()
        emit_bytecode(operator) // postfix arithmetic emit
\end{lstlisting}

Non-primitive operations such as multiplication (\texttt{*}) and division (\texttt{/}) are translated into standard OS subroutine library calls: \texttt{Math.multiply} and \texttt{Math.divide}.

\section{Lexical Scope Table Management}
% ============================================================

The compiler maintains a two-level scope architecture implemented in \texttt{LexicalScopeTable}:
\begin{itemize}
    \item \textbf{Class-Level Scope}: Tracks static variables (mapped to the \texttt{static} segment) and instance fields (mapped to the \texttt{this} segment).
    \item \textbf{Subroutine-Level Scope}: Tracks method/function arguments (mapped to the \texttt{argument} segment) and local variables (mapped to the \texttt{local} segment). This table is completely cleared at the beginning of each subroutine declaration.
\end{itemize}

Identifier resolution always checks the subroutine scope first, falling back to class scope. If the identifier is absent in both, the parser processes it as a class name (e.g. for static calls like \texttt{Output.println}).

\section{VM Stack Generation & Lowering}
% ============================================================

\subsection{Constructor Memory Allocations}

During class instantiation, the compiler determines the count of instance field variables. It emits a \texttt{push constant <fields_count>} instruction followed by a call to \texttt{Memory.alloc 1} to allocate memory on the heap, and pops the resulting base address into the \texttt{pointer 0} register to bind the target object context to the \texttt{this} segment. For \texttt{Conv.new}, three fields are allocated (\texttt{inputTensor}, \texttt{outputTensor}, and \texttt{inputSize}).

\subsection{Method Preamble and Invocations}

Methods operate on an active object instance passed implicitly at argument index 0. On entry, the method executes a preamble:
\begin{lstlisting}[style=vmcode]
push argument 0
pop pointer 0
\end{lstlisting}
This maps all references in the \texttt{this} segment to the object's instance fields. When compiling a method call, the compiler pushes the object reference onto the stack as the first argument, followed by the explicit arguments, and increments the argument count by 1.

\subsection{Safe Array Write Abstractions}

Array lookups use the \texttt{pointer 1} / \texttt{that 0} translation. However, array writes (e.g. \texttt{let a[i] = expr;}) require care because evaluating the right-hand side expression might contain array accesses itself, which would clobber the \texttt{pointer 1} register. To prevent this, the compiler pushes the base address plus the index offset onto the stack, compiles the right-hand side expression, pops the expression result to a temporary register (\texttt{temp 0}), updates \texttt{pointer 1}, and pop-assigns the value to \texttt{that 0}:

\begin{lstlisting}[style=vmcode, caption={Secure Array Write VM Bytecode}]
push arr           // push array base address
push index         // push index offset
add                // compute target address on stack
... evaluate expression ...
pop temp 0         // save expression output
pop pointer 1      // update THAT register with target address
push temp 0        // restore expression output
pop that 0         // RAM[THAT] = expression output
\end{lstlisting}

\subsection{Compilation Trace for \texttt{let outputTensor[outIdx] = cellVal}}

Using a 5$\times$5 matrix test case where the first output pixel yields a value of 7 at flat index offset 0, the compiler generates the following trace:

\begin{lstlisting}[style=vmcode, caption={Trace for Array Assignation}]
push this 1       // push outputTensor base address (RAM 2050)
push local 8      // push outIdx value (0)
add               // RAM[SP-2] + RAM[SP-1] = 2050
push local 7      // push cellVal accumulator (7)
pop temp 0        // temp 0 = 7
pop pointer 1     // THAT = 2050 (pop target address to pointer 1)
push temp 0       // push 7
pop that 0        // RAM[2050] = 7
\end{lstlisting}

The temporary register holds the output value while the destination address is safely loaded into the \texttt{THAT} base register, avoiding address clobbering.

\section{Convolution Application Design}
% ============================================================

\subsection{Algorithmic Choices}

\begin{description}
    \item[Stride Length ($S$)] Set to 1 in the constructor. Convolving a 5$\times$5 input with a 3$\times$3 kernel yields a 3$\times$3 output.
    \item[Filter Kernel] A 3$\times$3 Laplacian sharpening kernel \texttt{[0, -1, 0, -1, 5, -1, 0, -1, 0]}. This highlights high-frequency details by computing the difference between a pixel and its neighbors.
    \item[Flattening representation] Matrices are flattened into 1D arrays in row-major format:
    \begin{equation*}
    \text{Index}(r, c) = r \cdot \text{inputSize} + c
    \end{equation*}
\end{description}

\subsection{Output Boundary Calculations}

The spatial convolution output side dimension ($O$) is calculated as:
\begin{equation*}
O = \left\lfloor \frac{N - F + 2P}{S} \right\rfloor + 1
\end{equation*}
For $N = 5, F = 3, P = 0, S = 1$: $O = \lfloor 2/1 \rfloor + 1 = 3$. 
For $N = 9, F = 3, P = 0, S = 2$: $O = \lfloor 6/2 \rfloor + 1 = 4$.

\subsection{Asymptotic VM Instruction Complexity}

The 2D convolution algorithm runs four nested loops (two for the output grid dimensions, and two for the filter dimensions):
\begin{itemize}
    \item Outer loops run $O^2$ times.
    \item Inner loops run $F^2 = 9$ times (a constant).
\end{itemize}
The total iterations scale as $9 \cdot O^2$. Since $O = \frac{N - 3}{S} + 1$:
\begin{align*}
\text{For } S = 1: \quad & \text{Iterations} = 9(N-2)^2 = \Theta(N^2) \\
\text{For } S = 2: \quad & \text{Iterations} = 9\left(\frac{N-1}{2}\right)^2 \approx \frac{9}{4}N^2 = \Theta(N^2)
\end{align*}
Thus, changing the stride length from $S=1$ to $S=2$ decreases the absolute VM instruction count by approximately a factor of 4, but the asymptotic complexity in terms of the input size $N$ remains **exactly identical** ($\Theta(N^2)$). Stride only influences the constant coefficient factor.

\section{Bugs and Troubleshooting Observations}
% ============================================================

\subsection{The Method Argument Offset Bug}

During early integration, method calls generated corrupted variables. In Jack, method calls are compiled by pushing the parent object as argument 0, followed by the explicit arguments. A call like \texttt{convolutionEngine.initFilter(filterKernel)} must be compiled as \texttt{call Conv.initFilter 2}. 

Our initial implementation did not increment the argument count for method calls. The callee method read local stack values instead of the object reference, causing the method preamble to overwrite the parent's pointer segment. We resolved this by querying \texttt{self._scope_table.has_symbol(initial_identifier)} in the parser to distinguish method calls from static functions, and incrementing the argument count when an object reference was pushed.

\subsection{Handling Double XML Escapes}

We encountered a bug where character escaping resulted in double-escaped sequences. Iterating over the replacement mapping in an arbitrary dictionary order replaced the ampersand character \texttt{\&} in already-escaped entities (e.g. converting \texttt{<} first to \texttt{\&lt;}, then to \texttt{\&amp;lt;}). We resolved this by ensuring the ampersand character is replaced first, before any other entities.
